# 订单工作台与生产计划中心统一优先分配设计

## 目标

订单工作台与生产计划中心必须对共同出现的销售订单行给出相同的成品覆盖、生产需求、已安排和未安排数量。所有涉及客户订单之间争用成品库存、原料库存和在途供应的判断，统一以销售订单行交付日期为第一优先级。

两个页面的职责范围保持不变：订单工作台继续包含全部未履约订单，生产计划中心继续只包含需要生产处理、正在生产或完工待回补的订单。因此页面总行数可以不同，但共同订单的数量口径和相对顺序必须一致。

## 统一优先键

每条销售订单行使用以下稳定优先键：

1. 是否缺少交付日期：有明确交付日期的订单优先。
2. 销售订单行交付日期升序。
3. 销售订单创建时间升序。
4. 销售订单编号升序。
5. 销售订单行序号升序；无法取得序号时使用销售订单行名称升序。

缺少交付日期的订单排在所有有明确交付日期的订单之后，并继续显示“缺少交期”高风险。风险等级、缺料状态、生产状态、Production Plan 创建时间、计划开始时间和 Work Order 计划结束时间都不参与客户订单之间的库存与原料竞争。

页面搜索、筛选和分页只能在全量需求完成分配之后执行，避免当前可见记录改变分配结果。

## 成品库存分配

成品库存池按以下维度隔离：

```text
公司 + 成品编码 + 成品仓库
```

每条订单行先保留其有效 Stock Reservation Entry 数量。仓库当前未预留、仍可用于销售订单预留的成品库存，再按照统一优先键全局分配一次；同一份库存不能同时覆盖多张订单。

每条订单行继续使用以下数量关系：

```text
成品覆盖 = min(待交数量, 有效预留 + 本次优先获配的未预留成品)

生产需求 = max(待交数量 - 成品覆盖, 0)

未安排生产 = max(生产需求 - 活动工单剩余量, 0)

超计划生产 = max(活动工单剩余量 - 生产需求, 0)
```

分配是页面刷新时的只读软分配，不创建新的库存预留或自定义台账。实际执行预留、发货、创建生产计划或回补订单时，服务端仍须重新读取最新库存和订单状态。

## 原料与在途供应分配

原料库存池按以下维度隔离：

```text
公司 + 原料编码 + 原料仓库
```

已由 Production Plan 生成的 Work Order 继续作为直接用料和多级半成品关系的事实来源，但不同销售订单之间争用原料库存、Purchase Order 未收货数量和 Material Request 未下单数量时，改用关联销售订单行的统一优先键，而不是 Production Plan 或 Work Order 的计划时间。

同一份原料库存或在途供应只能分配一次。Purchase Order 先于 Material Request 分配；供应计划日期晚于销售订单行交付日期时，只显示为晚到供应，不能覆盖该订单的按期需求。

Production Plan 和 Work Order 的计划开始、计划结束时间继续用于工厂内部排产与执行展示，不改变客户订单之间的物料优先级。简化流程当前一个 Production Plan 对应一条销售订单行，因此直接使用该行交付日期；若读取到包含多条销售订单行的标准 Production Plan，则每条 Work Order 按其关联销售订单行分别参与分配。

没有 Sales Order 来源的手工生产计划不参与订单主列表的原料竞争，继续放在“其他生产”区域展示和处理。

## 共享计算边界

全局成品分配器必须位于订单履约公共计算层，由订单工作台生成全量订单行后调用。订单级汇总必须在分配完成后重建，不能继续汇总每张订单独立查询得到的可预留库存。

生产计划中心直接复用订单工作台已经分配完成的订单行，不得再次执行第二套成品分配。创建生产计划等写操作也复用同一分配结果，并在写入前重新计算。

原料覆盖使用同一个统一优先键生成订单需求顺序，再驱动 Production Plan Work Order 图的库存和在途供应分配。采购缺料页面继续保留跨订单汇总采购能力，但其订单来源和供应归属展示不得改变 ERPNext 原生数量语义。

## 页面展示

订单工作台和生产计划中心对共同订单统一显示：

- 有效预留数量；
- 按交付优先级模拟获配的未预留成品数量；
- 成品总覆盖；
- 生产需求；
- 活动工单覆盖；
- 未安排生产数量。

订单工作台按订单内最早的销售订单行交付日期排列一级订单，展开后的订单行按统一优先键排列。生产计划中心按销售订单行统一优先键排列生产需求。状态和风险只作为标签及筛选项，不改变展示顺序。

Production Plan 明细继续显示计划开始时间，但必须明确标注“物料优先依据：订单交付日期”。不新增“计划截止日期”字段，不修改 ERPNext/Frappe 核心 DocType。

纯库存覆盖且没有活动生产或完工待回补事项的订单仍不进入生产计划中心。页面顶部总数因此不要求相同，但应使用明确的指标名称区分“未完成订单”和“生产需求”。

## 边界情况

- 同一销售订单含多个产品行时，按订单行分别分配，再汇总为订单折叠行。
- 同一产品使用不同成品仓库时，库存池互不借用。
- 同一原料来自不同原料仓库时，原料池互不借用。
- 已实际预留的库存不因交付日期变化转移给其他订单。
- 销售订单交付日期变更后，下一次刷新重新计算尚未预留库存和原料的软分配。
- 相同交付日期的订单不依赖数据库返回顺序，始终使用创建时间、订单号和订单行进行稳定决胜。
- 缺少交付日期的订单不能自动抢占已承诺交期订单的库存或原料。
- 已开始生产的工单不因软分配变化回退执行状态，但页面必须显示其最新后续用料风险和可能的超计划数量。

## 代码边界

- 只修改 `custom_apps/process_simplification` 及对应设计、计划和测试文档。
- 不修改 ERPNext/Frappe 官方代码和核心 DocType。
- 不新增持久化库存分配表，不在页面加载时创建业务单据。
- 保留 Sales Order、Stock Reservation Entry、Production Plan、Work Order、Stock Entry、Material Request 和 Purchase Order 作为事实来源。
- 不实现产能排程、人工拖拽优先级或新的生产提前期模型。

## 测试与验收

- 两张订单共享一份只能满足一张的成品库存时，两个页面都把库存分配给更早交付订单，后续订单显示相同的生产需求。
- 已实际预留的数量始终保留给来源订单；仅未预留库存参与交付优先分配。
- 同交付日期时，输入顺序变化不改变分配结果。
- 缺少交付日期的需求排在有交付日期需求之后，且不抢占其库存。
- 两个页面共同出现的订单，其成品覆盖、生产需求、活动工单覆盖和未安排生产完全一致。
- 风险或状态变化不会改变库存获配结果。
- 搜索、筛选和分页不会改变全量分配结果。
- 原料库存以及同一张 Purchase Order、Material Request 的未完成数量不会同时覆盖多张订单。
- 原料优先顺序使用销售订单行交付日期，不使用 Production Plan 开始时间或 Work Order 结束时间。
- 订单工作台仍显示纯库存订单，生产计划中心仍排除没有生产事项的纯库存订单。
- 运行 `process_simplification` Python 单元测试、站点集成测试、前端测试和前端资源构建。

## 非目标

- 不创建自动库存预留或原料硬预留。
- 不改变销售订单交付日期本身。
- 不推导 Production Plan 开始时间或 Work Order 结束时间。
- 不改变采购供应商选择和合并采购规则。
- 不保证软分配在刷新后永久不变；实际业务写入仍以 ERPNext 提交校验为准。
