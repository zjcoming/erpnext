# ERPNext v16 工厂部署前置与回归记录

更新时间：2026-08-29

适用基线：ERPNext 16.33.0、Frappe 16.32.0、`process_simplification` v16 长期分支

旧版用例来源：[基于 v17 的历史测试用例](https://rcnz1aofm14f.feishu.cn/docx/C5BSda3QIomy0bxzBKvcX2zCnRd)

本文档只记录工厂部署前必须建立的数据、v16 与 v17 的差异、真实浏览器验收结果及已发现问题。账号密码不得写入本文档。

## 1. 固定原则

- 后续开发、部署和回归只基于 v16，不再兼容或参考 v17 的不稳定实现细节。
- 销售订单必须从 Custom App 的“快速开单”进入，不使用 ERPNext 标准“新建销售订单”作为业务入口。
- Customer、Item、Product Bundle、仓库、采购价格、工序计价规则等前置数据优先由 Administrator 在系统界面创建；不得用 SQL 或脚本伪造业务单据。
- Custom App 负责编排和简化入口，Sales Order、Production Plan、Work Order、Job Card、Material Request、Purchase Order、Purchase Receipt、Stock Entry 等仍以 ERPNext 标准单据为业务事实。
- 生产工人、生产主管和 Administrator 三个角色保持隔离，不通过授予宽泛 Manufacturing/System Manager 权限绕过问题。

## 2. `docstatus` 与“草稿”如何判断

### 2.1 可提交单据

只有 DocType 元数据中启用了“可提交”的单据才使用标准三态：

| 业务阶段 | `docstatus` | 示例 |
| --- | ---: | --- |
| 草稿 Draft | 0 | 未提交的 Sales Order、BOM、Material Request、Purchase Order、Purchase Receipt、Job Card |
| 已提交 Submitted | 1 | 已确认并进入业务流程的上述单据 |
| 已取消 Cancelled | 2 | 对已提交单据执行取消后的状态 |

因此，对这些单据查询“正式有效记录”时通常需要 `docstatus = 1`，但具体业务状态还要结合 `status`、`per_*` 等字段判断。

### 2.2 非可提交主数据和自定义流程记录

Product Bundle 在 ERPNext v16 中是非可提交 DocType。它保存后的正常生命周期仍然是 `docstatus = 0`，不会变成 1，也不存在“等待提交后才可使用”的业务草稿阶段。

Product Bundle 的正确可用判断是：

```text
disabled = 0  -> 可用
disabled = 1  -> 已停用
docstatus     -> 正常记录始终为 0，不用于激活判断
```

Frappe 列表页可能根据通用 `docstatus = 0` 显示“草稿”提示，这是通用界面标签，不等于 Product Bundle 需要提交。快速开单接口不得要求 Product Bundle `docstatus = 1`，也不得使用 v17 才存在的 `is_active` 字段。

Administrator 浏览器已核验 v16 真实记录 `_Test Product Bundle Item`：列表行同时显示通用提示“文档处于草稿状态”和业务状态“激活”；表单只有“保存”按钮、没有“提交”按钮，并以“禁用”复选框控制交易可选性。这正是非可提交主数据的正常表现。

同理，Job Card Worker Assignment、Job Card Work Report 等非可提交自定义记录使用自己的 `status` 字段表达 `Active`、`In Progress`、`Pending Approval`、`Approved`、`Rejected`、`Completed`，不能只用 `docstatus` 判断业务状态。

## 3. 三角色浏览器分工

| 浏览器 | 角色 | 主要验证范围 |
| --- | --- | --- |
| Google Chrome 插件 | Administrator | 创建主数据和业务前置、从生产计划中心按 Work Order 派工并指定审核主管、核验标准单据和库存事实 |
| Codex In-App Browser | 生产主管张三 | 从报工审核页全局派工、审核或驳回报工、核验主管权限范围 |
| Microsoft Edge 插件 | 生产工人李四 | 查看自己的派工、开始/结束计时、提交本人报工 |

部署时每个非 Administrator 用户必须同时满足：

1. User 已启用。
2. User 只持有对应的隔离角色。
3. User 关联一个状态为 Active 的 Employee。
4. Employee 的 Company 与 Job Card Company 一致。
5. 主管关联 Active Employee，或拥有明确的 Company User Permission。
6. 工人不得同时持有 Production Supervisor、Production Wage Manager、Manufacturing、Shop Floor 或 System Manager 等冲突角色。

## 4. Administrator 必须提前完成的系统设置

### 4.1 公司和仓库

- Company 默认在制品仓：`在制品仓 - 恒`
- Company 默认成品仓：`成品仓 - 恒`
- Stock Settings 默认/原材料发料仓：`原材料仓 - 恒`
- Item Default 中如配置了仓库，以 Item + Company 的设置优先。
- 自动生成 Work Order 时，成品工单收料到成品仓；半成品工单收料回原材料仓，供上层工单继续领料。

部署后必须抽查每张生成的 Work Order：

- `source_warehouse` 不为空且为原材料仓。
- `wip_warehouse` 为在制品仓。
- 最终成品 `fg_warehouse` 为成品仓。
- 半成品 `fg_warehouse` 为原材料仓。

### 4.2 Product Bundle 与快速开单

- Product Bundle 保存后即是 ERPNext 中的有效主数据，保持 `disabled = 0`。
- Product Bundle 的父物料与子物料必须存在并启用。
- 当前 v16 快速开单只支持普通销售成品，明确排除启用中的 Product Bundle；它不能因为 `docstatus = 0` 或缺少 v17 `is_active` 字段而查询报错。
- 本轮不跳转标准销售单，因此测试产品必须是带有效 BOM 的普通销售成品；Product Bundle 若要纳入快速开单，需要另立需求补齐组合子项的库存、生产和预检语义。
- 快速开单创建的 Sales Order 必须能回链 Customer、Item 和需求日期。
- 当前 Stock Settings 使用 `Item Code` 作为物料主键；数字是 `Item.item_code`，用于 BOM、库存、采购、生产和销售单据关联，不是快速开单生成的临时 ID。
- 工厂初始化时必须为每个 Item 维护可识别的 `item_name`，不得直接复制物料编码充当名称。已发生业务的物料编码原则上保持稳定；名称可以按工厂常用叫法补充和修正。
- 快速开单、订单工作台、生产计划中心和缺料采购统一“名称优先、编码带标签”显示。若 `item_name` 为空或等于 `item_code`，页面显示“名称待维护”并可进入物料主数据处理，不擅自依据 BOM 层级编造名称。

### 4.3 采购价格

- 真实采购前必须为采购物料建立有效 Supplier/Item Price，或在 Purchase Order 中录入合法单价。
- 不建议全局关闭 ERPNext 的“采购周期保持相同费率”校验。
- 零单价 Purchase Order 会导致 Purchase Receipt 无法通过改价补救；正确做法是取消错误 PO，修正价格后创建修订 PO。

### 4.4 工序、工作站和计价规则

- Job Card 的 Operation、Workstation、Work Order Operation row 必须完整。
- Manufacturing Settings 中“生产任务单实际工时强制填写开始与结束时间”必须关闭；Custom App 由服务器记录开始/结束时间并计算实际分钟。
- 每个允许派工的 Operation 必须恰好有一条在生产日期有效且 `enabled = 1` 的 Operation Wage Rate。
- 计件规则按批准数量计价；计时规则按服务器计算的批准分钟计价。
- 计价规则有效期不可直接修改，应新建不重叠的替代规则。
- 浏览器本地日期和站点记账日期可能相差一天；有效期和生产日期以站点日期为准。

本次回归由 Administrator 在界面中创建并实际使用的计件规则：

- `OWR-2026-00001`：注塑骨架，从 2026-08-29 起生效，1 CNY/件。
- `OWR-2026-00009` 至 `OWR-2026-00019`：骨架插针（委外）、绕线圈、线圈浸锡点胶、焊接、装配、注塑外形、校检凸点、烘箱加热检测、检测电阻、检测耐压匝间、激光打标；均从 2026-08-29 起生效，1 CNY/件。
- `OWR-2026-00002`：历史注塑骨架规则，有效期为 2026-08-01 至 2026-08-28。

新旧规则没有日期重叠，避免同一天出现多条有效价格。

### 4.5 记账日期

当浏览器日期与站点日期不同，Purchase Receipt、Stock Entry 等标准单据如果要使用指定日期，保存或提交前应勾选“修改记账日期与时间”，再输入站点接受的日期时间。否则 ERPNext 可能重置日期或触发异步确认。

- 中国工厂的 System Settings 时区必须明确设置为 `Asia/Shanghai`，不能保留 Frappe/ERPNext 测试环境的 `Asia/Kolkata` 默认值。
- 部署和回归前执行 `bench --site <site> execute frappe.utils.get_system_timezone`；时区错误会同时影响“今日已处理”、报工生产日、每日工时上限、计价规则生效日和月工资归属。
- 不得在长期使用的开发或生产站点执行会初始化 ERPNext 测试数据的全量测试；共享开发站点回归必须使用 `--skip-before-tests`，完整初始化放在可丢弃的独立测试站点。

### 4.6 生产计划中心派工

- Administrator/System Manager 在“生产计划中心”展开销售订单后，可直接在每张 Work Order 卡片操作。当前可开工、已发料或生产中的工单显示主按钮“派工”；等待半成品、待采购等未就绪工单显示次按钮“预派工”。已完成、已停止、已关闭或已取消的工单仅在当前用户有权查看历史派工时显示“查看派工记录”；主数据阻塞、缺少生产任务、状态未知以及未纳入生产计划的旧工单不显示派工入口。
- 弹窗必须限定到所点 Work Order 的 Job Card，并同时展示工序、工作站、任务量、已完成量、当前可报量、物料状态、已有工人和审核主管，避免再到全局列表人工搜索工单。
- Administrator 代派工且该 Job Card 尚无活动派工时，必须选择后续审核主管；已有活动派工时主管自动锁定，保证同一 Job Card 的所有工人由同一主管审核。
- 生产主管仍从“报工审核”使用全局“新增派工”，不因此获得生产工作台或标准 Manufacturing 页面权限。
- 未发料允许预派工，但工人页面必须显示“等待发料”并禁用开始计时。发料覆盖、计价规则和 Job Card 可用性仍由服务端在每次动作时重新校验。
- 同一 Job Card 可以派给多个工人共同完成，但已派给该 Job Card 的工人不会再次出现在候选列表中。

## 8. 工厂部署顺序

1. 部署固定的 v16 代码、镜像和 Custom App 提交。
2. 安装 App 后执行 `bench --site <site> migrate`。
3. 执行 `bench --site <site> clear-cache` 和 `clear-website-cache`。
4. 执行 `bench build --app process_simplification`，重启 Web、Socket.IO、Scheduler 和 Worker。
5. Administrator 依次创建 Company、仓库、Customer、Item、Product Bundle、BOM、Operation、Workstation、Supplier、采购价格和工序计价规则。
6. 创建并核验张三、李四对应的 User、Employee、角色和 Company 范围。
7. 在三个独立浏览器中登录三个角色，避免反复切换账号。
8. 只从“快速开单”创建第一张验收 Sales Order。
9. 完成生产计划、缺料采购、收货、工单发料、派工、报工、审批和成品入库闭环。
10. 若销售订单被关闭或撤销，必须同时检查并取消关联 Production Plan/Work Order；不能只把 Work Order 标记为 Stopped。
11. 在生产计划中心执行“回补订单”（或在订单工作台执行等价的完工成品预留），再从订单工作台创建、提交发货单。
12. 对照本文证据核验标准单据编号、仓库、数量、价格、状态和审计人员。

六个受影响自定义 Page JSON 的 `modified` 时间戳必须随代码一并发布并执行 migrate：四个页面用于刷新按钮缓存修复，快速开单和缺料采购用于 POST 请求方式更新。这样 v16 客户端重新加载页面时会按新时间戳淘汰旧 Page 脚本，无需人工修改浏览器本地存储。

### 10.4 仍需工厂现场决定或实物 UAT 的边界

以下项目不能仅靠当前开发数据宣称已经完全验收，部署时必须按工厂真实流程补测：

- 已提交 Delivery Note 与 Purchase Receipt 的“取消”仍需工厂现场按审批制度验证；销售退货、采购退货、重新预留、再次发货和再次收货已由本轮真实单据覆盖。取消属于破坏性操作，现场执行前必须再次确认目标单据。
- 质检不合格、返工 Job Card、报废/工艺损耗和替代料。这些目前不是 worker reporting v1 支持范围，不能用普通报工绕过。

- 序列号/批次、复杂多 UOM、委外和 `skip_transfer = 1` 的直接消耗生产。`skip_transfer` 由 ERPNext 在制造入库时校验库存，本次新增的“先发料后报工”限制不适用于该模式。
