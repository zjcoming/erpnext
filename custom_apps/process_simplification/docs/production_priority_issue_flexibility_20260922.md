# 生产发料：补齐部分可发料状态下的优先级调整入口

原有系统已经按销售订单交期计算物料建议分配，并支持负责人调整优先级申请发料。问题发生在 `partially_ready` 状态：前端提前返回“申请部分发料”，没有同时提供已有的调整入口。此时即使还有未正式预留的库存，页面也只能按建议量申请。

本次复用原有后端动作和预留机制：

- 存在优先分配影响、且可部分发料时，同时提供“按建议申请部分发料”和“调整优先级并申请发料”。默认动作仍按建议量申请；调整动作按服务端复核后的实际可锁定量申请。
- 原先等待物料、部分发料后的调整入口继续保留。已终止工单、已有待处理申请、无需发料及仅有正式预留限制的情况不增加调整入口。
- 调整确认展示可能受影响的工单、交期、物料与数量上限。说明申请成功时正式预留、库房提交发料单后扣库存，以及其他单据的正式预留不可占用。影响提示来自当前页面快照，实际申请仍由服务端重新校验。
- 直接用料区分别显示“仓库现存（含已预留库存）”“按交期建议分配”“本单已预留”“按建议仍缺”，保留总需求和待备料数量。
- 沿用生产负责人权限。仅有库存查看权限的用户不获得申请或调整按钮。相邻操作按钮样式及 CSS 版本一并更新。

## 验证

前端 `production_workbench.test.js` 共 47 项通过，包括两个动作并存、默认数量和覆盖标志分离、正式预留限制、终止和待处理状态、只读角色不显示按钮，以及确认内容的 HTML 转义。

在本地隔离站点 `hs-wb-actions.localhost` 通过原生单据创建两单 30 / 100 件、每件用料 10 克、来源仓库存 1,000 克的情形。3 项事务验证通过，测试单据回滚：

| 情形 | 结果 |
| --- | --- |
| 第二单按默认建议申请 | 草稿用料 700 克，正式预留 700 克；重复申请复用同一草稿 |
| 第二单调整优先级申请 | 草稿用料 1,000 克，正式预留 1,000 克；第一单缺口变为 300 克，并保留影响记录 |
| 第一单已正式预留 300 克后，第二单调整 | 第一单的 300 克受保护，第二单最多申请并预留 700 克 |

上述三种情形在发料草稿阶段，来源仓实际库存仍为 1,000 克。没有以草稿或预留代替实际库存扣减。

使用当前组件和工作台样式在浏览器做本地渲染检查，桌面与 390 像素 iframe 宽度下均能显示两个入口；窄屏文档宽度和内容宽度均为 390 像素，确认内容展示受影响工单、交期和数量。该检查为组件渲染与提示验证，不等于真实角色浏览器全链路、实体手机或工厂验收。

本地证据目录：`outputs/priority-allocation-flexibility-20260922/`。包含事务验证脚本 `verify.py`、结果 `transactions.log`、前端测试结果 `frontend.log` 和组件预览生成脚本 `render-preview.cjs`。

## 发布边界

改动仅在本地工作区，未部署生产，未执行真实工单的发料、预留或优先级调整。生产发布后需由实际生产负责人确认两种入口和提示，并由库房完成一次申请至发料的岗位验收。
