# 流程简化页面更新设计：4 核 8G、21–50 人

状态：2026-09-09 已实现并在开发站点验证；4 核 8G 云端混合负载压测尚未进行。用户确认高峰 21–50 人；本地先前的实时连接问题由未放开 9000 端口导致，不作为云端必须轮询的理由。手机锁屏推送暂不做。实施与验证边界见 `page_refresh_validation_20260909.md`。

## 设计结论

复用 Frappe 的实时连接和 Redis：业务提交后告知相关用户“哪类数据有变化”，当前可见页面按计算成本合并刷新，未变化时不重查业务数据。只保留一个低频的版本补查入口，用于漏事件和断线恢复。通知提醒与页面数据更新分别处理；关闭提示音或没有通知日志，不应阻止页面更新。

4 核 8G 是本方案的部署目标，不是已验证的容量结论。50 人在线不等于 50 个持续执行计算的请求；未完成订单量、BOM 层级、库存流水量及报工峰值也需要纳入上线压测。

## 页面更新规则

以下秒数是初始设计参数，均指“发生相关变化后”的调度策略，不是固定周期全量重算。连续事件不能无限延后刷新；采用有最长等待的合并调度。

| 页面 | 自动更新内容 | 建议策略 |
|---|---|---|
| 我的任务、正在做 | 本人的任务、数量、审核结果及可开始状态 | 收到相关变化后合并约 1 秒更新；连续变化最多每 3 秒请求一次；计时显示在本地更新 |
| 报工审核、异常审核 | 当前待办及当前页必要状态 | 合并约 1 秒，连续变化最多每 5 秒一次；历史区独立，未查看时不查询 |
| 库房工作台、采购待办 | 当前队列及受影响的分类状态 | 合并约 1 秒，连续变化最多每 5 秒一次；保持公司、队列、筛选和分页 |
| 订单工作台、生产计划中心 | 当前可见列表和相关汇总 | 首次变更可尽快更新；持续变更时完整计算最多每 30 秒一次，等待期间显示数据正在更新 |
| 缺料采购 | 当前公司采购缺口 | 浏览状态采用最多每 30 秒一次的合并重算；已有勾选/输入时提示数据变化，保留用户操作 |
| 快速开单、供应商分配、报工/审批弹窗 | 保留输入，仅标记依赖数据已变化 | 不自动覆盖输入或刷新整页；确认提交前重新核验数量、库存、权限和单据状态 |
| 经营总览 | 当前公司、期间的统计 | 相关变化后合并，最多每 120 秒一次；始终显示本次统计时间 |
| 历史记录、库存查询报表、工资查询 | 当前查询结果 | 默认进入或主动查询时加载，相关变化仅标记结果可能有更新；工资确认等写操作重新校验 |
| 设置、权限管理 | 当前编辑内容 | 不定时重载；权限变化使该账号的相关缓存失效，下次读取/操作按最新权限核验 |

手动刷新、用户本人操作成功后的刷新仍可立即执行，但要复用正在进行的请求并受服务器并发保护。刷新只换数据，不使用 `window.location.reload()`：保留搜索、分页、展开项、滚动位置、选中状态、弹窗和已启用的提示音。自动读取不加全屏遮罩，不清空旧表格后再等待返回。

## 一条业务变化如何传到页面

1. 在事务成功提交后，标记受影响的数据类别并发布轻量事件；失败或回滚不发布。事件只包含经授权的范围和变化类别，不携带订单金额、工资、客户或库存明细。
2. 复用现有用户实时通道，按实际员工、主管、公司及仓库权限定位接收范围。读接口仍独立执行权限检查，不能依赖“收到了事件”作为授权。
3. 当前页面登记自己关心的数据类别。别人的报工不触发无关工人的页面重读；历史页不因为新派工而反复请求。
4. 客户端合并短时间内的重复事件。同一页面最多一个数据请求进行中；请求期间再次变化，只记录一次待更新，按刷新间隔补一次，不能丢掉后到的变化。
5. 页面隐藏或切走时停止业务查询；返回前台和重连后统一查版本，再更新确实变化的当前页面。旧路由/旧筛选的迟到响应不能覆盖新页面。

首批依赖应至少覆盖：派工/撤销/重新分配、开工暂停与报工、审批退回与通过、发料/退料/补料/完工入库、销售订单及预留/发货/退货、采购申请/订单/收货及取消、BOM/默认仓库/影响履约的设置变更。共享库存会影响后续订单，所以入出库和预留变化需要使相关公司范围的履约/缺料结果失效，而不是只刷新被操作的那一张订单。

变化来源应覆盖标准单据、流程简化 API、后台任务。原生 ORM 的单据更新可复用原生事件；绕过 ORM 的 SQL/批量更新要在业务完成点显式标记变化，不按每条物料或每条流水重复发布。一次事务中相同类别/范围只标记一次。

## 断线兜底与请求量

- 一个前台页面只有一个统一检查入口，同时检查通知与当前页面所需的数据版本。
- 实时连接正常：每 120 秒做一次轻量版本补查；实时事件仍立即驱动相应页面。
- 实时连接断开、HTTP 可用：每 30 秒检查一次版本；前台恢复、网络恢复和重连立即补查。相较当前 10 秒补查，这是拟调整参数，断线期间可能多等约 20 秒。
- HTTP 也失败：30 → 60 → 120 秒退避，加少量随机间隔；恢复网络后立即重试。隐藏页面停止请求，避免多设备整点同时发起。
- 版本读取优先使用已有 Redis，包含账号/权限范围的版本和实例代号。版本未变化时不读取完整通知列表，不查库存或 BOM；认证和权限校验仍有正常请求开销。
- 服务重启、Redis 版本丢失、未知版本均视为需要同步；权限和日期边界变化也需触发检查。缓存有短期失效上限，不能永久信任客户端旧结果。

50 个前台页面全部静止时：正常连接约 `50 / 120 = 0.42` 次检查/秒；全部实时断开时约 `50 / 30 = 1.67` 次检查/秒。它们只是版本检查的平均值，不包含业务操作、变化后的取数、认证、重连突发或其它 ERPNext 请求，不能当成整机负载测量。每个浏览器隐藏标签页暂停；多个可见窗口仍计为多个页面。

## 计算和缓存边界

- 优先消除同一请求内的重复计算，拆开待办和历史读取，再增加短期展示结果缓存。缓存键至少包含站点、账号、权限版本、公司、查询条件、业务数据版本和相关业务日期；不同用户不能只凭角色相同就共用结果。
- 列表分页/筛选可复用同一账号已经计算的安全结果；不能为每次翻页重新执行同一套完整分配。需要全公司供需分配的算法保持现有口径，不因显示分页截断供需集合。
- 连续变化时允许在明确标注更新时间的情况下暂时展示上一份只读结果，下一次合并刷新再计算最新状态；同一缓存范围同时只有一份计算进行中，其他请求复用结果或获知正在更新，避免全部阻塞 Web 进程。
- 计算开始和完成时核对数据版本；中途又有变化时不能把旧计算标为最新，只保留待更新状态。设置缓存过期和异常恢复路径，避免只依赖某条实时消息。
- 提交、审批、预留、发料、收货、采购数量确认等操作，继续走原有服务器权限、当前状态与数量校验及必要锁定，不以展示缓存作为业务通过依据。
- 第一阶段只使用现有 Frappe Web、Socket.IO、Redis 和队列。若压测发现单次重算已明显占用请求进程，再将该类只读重算放入现有后台队列，按范围合并任务并限制重算并发，不先增加独立服务。

## 云端与实施次序

正式部署使用生产配置，页面和 `/socket.io` 经同一个 Nginx 入口转发。9000 可保留为内部服务端口；这与本地开发时直接暴露 8000/9000 的接入方式不同，不需要重写 ERPNext 的实时服务。

1. 先做统一页面刷新控制和受影响范围事件，接入任务、审核、库房；拆开审核待办/历史，并保护输入状态。
2. 再接订单、生产、缺料，完成请求内计算复用、合并刷新、展示缓存及提交前的新鲜数据校验。
3. 将原通知完整轮询合并到统一版本检查，最后接经营总览与历史页的更新标记。
4. 在独立测试环境按 50 人混合角色验证：持续在线、连续报工/审批、同时打开生产总览/缺料页、断线重连、切回前台、取消单据、权限变化、正在编辑和输入期间发生外部变化。

验收应同时记录每个接口的请求次数、p95 耗时、数据库慢查询、CPU、内存和队列积压。目标是静止页面不执行重业务查询、无关用户不被刷新、批量业务不会造成逐条全量重算，并且正常网络下任务/待审通常在数秒内更新。实际云端未进行这些测试前，不声称已验证 4 核 8G 可稳定承载 50 人。
