# 通用单据扫码第一版实施计划

日期：2026-09-11
状态：代码已实现，并按用户确定的内部使用范围切换为无访问地址的单据码；已在开发站点启用并验证，硬件及完整业务流程验收待现场执行。实施结果见 [单据扫码说明](document_scan.md)。
范围：统一入口 + 采购订单 / Job Card 二维码 + 准确定位 + 人工确认操作。

## 1. 目标与已确定的产品行为

现场人员拿到纸质单据后，可以通过手机摄像头或电脑上的扫码入口找到系统内对应单据，继续使用原有业务操作。

| 对象 | 扫码后的行为 | 后续操作 |
| --- | --- | --- |
| Purchase Order / 采购订单 | 校验读取权限后打开对应采购单原页，显示当前状态与收货进度 | 用户自行点击现有收货入口、核对本次数量并提交 |
| Job Card / 生产任务单 | 刷新当前用户的任务，按 `job_card` 匹配派工，进入对应任务列表并定位、展开、高亮 | 用户自行点击现有开工、暂停、报工等按钮 |

生产任务定位规则：

- 任务有 `active_report`：进入“正在做”页面；暂停任务仍属于此页。
- 没有 `active_report`：进入“待开始”页面的现有分组，包括可以开始、待处理、等待发料。
- 目标在折叠的等待发料分组内时，先展开外层分组，再展开任务详情，最后滚动定位。
- 未匹配到当前用户的有效任务：提示“这张任务单不在你当前可操作的任务中，请联系主管确认。”
- 不将“当前列表没有匹配项”推断为“从未派单”。第一版不新增历史派工原因诊断。
- 第一版 Job Card 码按当前用户的派工定位；不增加管理人员专用的另一套生产详情跳转规则。
- 定位后继续显示现有待审核、前序工序未完成、等待发料等原因。派工变化后的最终操作资格仍由原接口重新校验。

## 2. 入口与设备

新增一个“扫一扫”入口，放在登录后的公共导航位置，并提供独立的扫码页面作为手机、电脑共同入口。用户不必先进入采购或生产页面。

| 方式 | 第一版行为 |
| --- | --- |
| 手机 / 平板 | 用户主动点击后申请摄像头权限，优先使用后置摄像头 |
| 电脑摄像头 | 同一入口启动摄像头，提供可用设备选择 / 回退处理 |
| 电脑二维码扫码枪 | 扫码页提供明确的输入框，支持键盘输入模式的二维码扫码枪及回车确认 |
| 手工输入 | 支持粘贴本系统内部单据码，与扫码共用解析流程 |
| 手机系统相机 | 只得到文本码，没有直接访问系统的网址；员工登录系统后使用系统内“扫一扫” |

不在整个系统页面上拦截所有键盘输入；扫码枪输入仅在扫码输入框取得焦点时接收。公共入口在手机和桌面页头均显示绿色“扫一扫”按钮，业务页菜单也保留入口，工人无需退出“我的任务”即可扫码，使用同一套识别与定位逻辑。

摄像头失败、权限被拒绝、没有可用设备时，显示可理解的提示，并保留输入框。关闭扫码窗口或识别成功后释放摄像头。一次扫描只处理一个目标，防止识别回调重复触发导航。

扫码页显示实时相机画面、与实际识别范围一致的四角框和扫描线，尺寸变化后重新对齐。成功找到可访问单据时播放一次短提示音，提供开关并尊重账号静音设置；无权限、识别失败和过期响应不播放成功音效，声音不可用不阻止导航。

## 3. 二维码格式与打印

采用纯文本内部单据码，不携带访问地址：

```text
HSERP|1|<32 位小写十六进制系统标识>|purchase-order|<单据编号的 UTF-8 base64url 编码，无填充>
HSERP|1|<32 位小写十六进制系统标识>|job-card|<单据编号的 UTF-8 base64url 编码，无填充>
```

系统标识在安装 / 迁移时一次生成并持久保存在站点全局默认值中，不受用户默认值影响，更换访问域名、IP 或端口不改变标识。备份恢复保留标识；从数据库克隆独立工厂时应重新初始化新工厂的标识并重印单据。该标识是公开的命名空间，不提供权限或保密能力，后端仍须检查当前会话。

- 允许的类型只有 `purchase-order` 和 `job-card`。前后端均验证完整码，拒绝其他系统标识、未知版本或类型、非法格式、异常长度以及所有网址码。
- 码内只包含定位信息，不携带登录凭据、可代替权限的令牌、数量、价格或派工状态。
- 状态在扫码后重新读取。同一采购单分批到货重复使用同一个码。
- 新建未保存单据不生成码；已保存草稿可以定位，后续操作按原有单据状态限制。
- 第一版以原生单据编号作为身份，不新增二维码台账或单据字段。若以后允许单据改名，旧纸质码需重印；修订后新编号生成新码。
- 表头右上方预留 28 mm 的二维码区域，保留白色静区，使用黑白输出，下方标注“仅限系统内扫码”及可读单号。
- 公司名称、地址、Logo 继续自动读取公司设置；二维码随单据变化。
- 服务器使用现有 PyQRCode / pypng 生成 PNG，每模块 8 像素，保留 4 模块静区，不使用外部二维码服务。联调发现当前 wkhtmltopdf 对 SVG 的输出可导致无法解码，因此实际实现使用 PNG。
- 本版覆盖采用“工厂简洁表头”的采购订单和 Job Card。关闭表头或完全自行排版的打印格式需另外接入，不能宣称全部打印格式自动覆盖。
- 同名已保存表头如果有用户修改，不直接覆盖。只对可确认的旧版受管模板升级，其他情况提供独立二维码片段供接入。
- 旧版网址码停用，旧路径只显示重印提示，不自动查单；已有 PDF 和纸质单据需重印。不提供网址码兼容入口。

## 4. 当前代码基础

核查基线：`rc/develop-v16`，HEAD `1ee6e3cced`，以及本次会话中已有的未提交工厂表头修改。该基线仅说明本地工作区，不代表线上部署版本。

| 已有能力 | 代码位置 | 本版使用方式 |
| --- | --- | --- |
| 摄像头扫码 | Frappe 已打包的 html5-qrcode | 直接复用识别库，补齐设备选择、错误提示及离页释放 |
| 二维码生成 | Frappe 依赖 `PyQRCode` | 新增本应用的打印辅助函数，原库已离线生成验证 |
| 登录与页面权限 | Frappe `www/desk.py`、原生会话及 Page 权限 | 员工先登录再扫码，后端拒绝未登录解析请求 |
| 采购单生成收货单 | ERPNext `buying/doctype/purchase_order/purchase_order.py::make_purchase_receipt` | 原页中的业务入口继续使用原映射、权限与数量规则 |
| 当前用户派工 | `api/production_reporting.py::get_my_dashboard`、`production_reporting/service.py::get_worker_dashboard` | 使用当前员工的 Active 派工及现有状态计算 |
| 任务分组与卡片 | `public/js/worker_reporting.js` | 复用 `partitionWorkerAssignments`、`data-assignment`、任务详情展开区 |
| 两个员工任务页 | `page/my_production_reporting/`、`page/active_production_work/` | 接收定位目标，刷新后定位对应派工 |
| 工厂表头 | `printing.py`、`templates/print/factory_letterhead.html` | 增加允许类型的动态二维码区域 |

ERPNext 自带的 `stock.utils.scan_barcode` 识别物料、序列号、批次、仓库；本版不将单据码送入该接口，避免触发物料表格填充等不相关行为。

全部新增业务逻辑放在 `process_simplification`，预计不需要修改 ERPNext / Frappe 核心代码或库存、财务表结构。

| 文件 / 模块 | 改动 |
| --- | --- |
| 新增 `public/js/document_scan.js` | 统一扫描交互、输入解析、重复回调防护、摄像头释放、导航 |
| 新增 `page/document_scan/` | 公共扫码页面、输入框、旧网址码停用提示、结果提示 |
| 新增 `document_scan.py`、`api/document_scan.py` | 纯文本码生成与完整解析、系统标识校验、采购单读取权限及本人派工校验；不提供任意 DocType 查询接口 |
| `install.py`、`hooks.py` 与必要的导航配置 | 安装 / 迁移时持久化系统标识，登录 boot 提供标识，加载公共入口及 Jinja 辅助函数，沿用现有角色 |
| `printing.py`、`templates/print/factory_letterhead.html` | 生成二维码、增加打印布局、处理未保存单据和非支持类型 |
| `public/js/worker_reporting.js` | 扫码目标匹配、按现有状态决定列表、刷新后展开与定位 |
| 两个员工任务页面 | 按需传递、接收定位目标；优先把共用代码放在 `worker_reporting.js` |
| `public/css/process_ui.css` 或独立扫码样式 | 扫码入口与临时高亮样式，兼顾手机触摸和桌面输入 |

生产匹配必须使用当前会话授权获取的派工结果；不新增查询任意员工任务的接口。优先在任务页正常加载流程中匹配目标，避免扫描页与任务页重复重算整份看板。

## 6. 实施顺序与完成条件

### 阶段 A：扫码协议和入口

1. 重新确认工作区差异、当前站点版本和摄像头所需的 HTTPS 访问条件，保留已有表头工作及其他未提交修改。
2. 实现持久系统标识、两种类型的内部码生成和完整解析，处理编号编码、非法输入、其他系统标识及旧网址码。
3. 实现公共入口和扫码页面，接入摄像头、输入框、扫码枪回车输入。
4. 接通登录后的扫码解析、旧网址码停用提示、摄像头关闭和重复扫描防护；未初始化系统给出升级提示。

完成条件：同一个内部码从系统内摄像头或输入框进入，能够解析到同一个单据目标；换域名仍有效，旧网址码不再查单；只产生读取和导航。

### 阶段 B：采购与生产定位

1. 采购订单校验读取权限后打开原页，使用现有状态和收货入口。
2. Job Card 匹配当前用户派工，按现有 `active_report` 等字段决定目标列表。
3. 数据渲染完成后展开外层分组、任务详情，滚动并短暂高亮；清除已经消费的定位状态。
4. 没有匹配、无权限、接口失败分别给出合适提示。导航期间发生派工变化时允许重新读取，不作成功定位的假提示。

完成条件：生产端只增加查找和定位，所有开工、报工、暂停、审核动作仍由用户在原页面触发。

### 阶段 C：打印接入

1. 将动态二维码加到工厂表头指定位置，提供单号文字回退。
2. 检查公司长名称、Logo、地址缺失等不同表头组合。
3. 在实际 PDF 运行环境检查中文字体和二维码输出，验证 A4 与多页文档。
4. 只启用目标表头，核对公司默认表头及已有单据的选择，保留用户自定义内容。

完成条件：采购订单与 Job Card 打印码不同且目标准确，打印后的纸张能够在受测设备上识别。

### 阶段 D：回归与现场验证

完成下列验收矩阵后，记录实际代码版本、站点、账号角色、设备、浏览器、扫码枪型号及结果，再决定上线范围。

## 7. 验收矩阵

| 范围 | 必须验证的情形 |
| --- | --- |
| 解析 | 两种支持类型、中文与特殊字符编号、非法码、其他系统标识、旧网址码拒绝、重复识别回调、域名变化后新码仍有效 |
| 登录与权限 | 已登录；未登录解析被拒绝；另一家公司或无读取权限账号；无员工身份账号；未初始化不生成临时码 |
| 采购 | 未收、部分收货、已收完、草稿、已取消 / 关闭；确认扫码本身没有新增收货单或库存变化 |
| 生产正常定位 | 已派给本人且可开始、进行中、暂停；定位正确卡片而不是同工单另一工序 |
| 生产受限状态 | 等待发料、前序工序阻塞、待审核；自动展开正确分组并保留原有禁用按钮和原因 |
| 生产无有效任务 | 未派给本人、派工撤回 / 释放后不再可见、任务不在当前列表；提示不泄露其他员工信息 |
| 刷新与状态变化 | 页面已经打开后再扫、连续扫两张不同单据、定位加载中派工变化、刷新后不重复跳页或滚动 |
| 人工操作 | 采购部分收货一次；本人任务开工与报工各一次；扫描阶段没有自动提交、修改数量或开始计时 |
| 摄像头 | Android 与 iPhone 真实设备；首次授权、拒绝、关闭后重开、切换页面释放摄像头 |
| 桌面 | 一种桌面浏览器摄像头；一台实际二维码扫码枪的键盘输入与回车；未聚焦时不干扰其他表单 |
| 打印 | 实际服务器 PDF、单页与多页、长公司名和 Logo；不同单据码内容准确；A4 实际纸张扫码 |

自动化检查至少包括：Python 解析 / 权限与打印生成测试，JS 定位 / 分组展开 / 重复回调测试，相关已有员工任务页面测试，以及受影响的资产构建与差异检查。真实角色、真机、扫码枪、PDF 纸张验证分别记录，不能互相替代。

## 8. 第一版边界与上线条件

- 业务动作均由人工确认；本版没有扫码即收货、自动报工、自动开工或批量自动提交。
- 不增加扫码枪厂商 SDK、专用手机 App、外部二维码服务、离线收货或离线报工。
- 不通过扫码扩大账号权限，不放开员工查询其他人的派工。
- 二维码没有对外访问地址，此行为不改变系统的网络可访问范围；内网或 VPN 限制由现有部署负责。
- 不将生产工单 Work Order 当成 Job Card；其他单据类型以后按同一协议逐步扩展。
- 开发站点现已运行并启用；开发容器已安装 Noto CJK 字体，生产镜像 Dockerfile 已增加该依赖。正式手机使用仍需可访问的 HTTPS 地址。
- 正式启用前完成目标表头备份及恢复办法，确认入口关闭 / 代码回退时不影响原有手工找单和业务流程。
- 代码合入、站点部署、真机验收、扫码枪验收分别记录状态；本计划不代表这些工作已经完成。

## 9. 复杂度判断

按以上收敛范围，开发复杂度为中低到中等：主要新增公共扫码入口、受控路由和任务定位。生产端不重写派工或报工服务。

主要不确定性在现场条件与验证：HTTPS / 登录入口、摄像头兼容性、纸张码的识别、已有打印格式差异。应按阶段 A-D 验收推进，不以生成一张二维码或单次扫描成功作为完整完成标准。
