**工序集中派工：低影响实施方案与风险评估**

日期：2026-09-28。代码基线：`cf72f3dd70`，以本次本地源码为准。

状态：9 月 28 日首版在 `codex/operation-dispatch-pool` 分支实施时默认关闭；10 月 7 日已改为默认开启，保留显式关闭能力。本文保留首版方案依据；现行交付范围与启停方式见[生产效率实施方案](production_efficiency_20260930.md)。首版设计阶段未读取生产数据库、未修改线上配置或业务数据。

用户目标：工厂多数工序有固定人员或班组，偶尔调人。希望减少找单、重复选人和逐单操作，同时尽量降低库存、工资、批次及历史业务风险。

建议先交付“按工序集中查看＋复用本轮人员选择＋批量确认首次派工”。保留现有生产规则和业务单据，先通过操作入口减少重复工作。默认人员的长期配置可以在这个入口稳定后补充；后台自动派工另行评审。

**先把当前能力说明准确。**

| 环节 | 当前代码行为 | 对方案的约束 |
| --- | --- | --- |
| 工单计划 100 件，先申请覆盖 40 件的物料 | 支持部分发料申请；申请创建草稿并预留，库房提交后才实际转仓 | 保留现有功能、数量口径与优先级规则；40 是可覆盖产量，不是所有原料各发 40 |
| 只发了部分物料，首次正式派工 | 普通转 WIP 工单仍要求整单净发料齐套 | 不能把“可部分发料”显示为“可首次派工” |
| 已有有效派工，当前净物料覆盖只剩部分数量 | 在个人剩余额度、前序、状态等条件满足时，可按物料覆盖量开工和分次报工 | 已有能力直接复用；不是要重新开发全部数量保护 |
| 待审核、已审核报工及生产损耗 | 占用相应数量，完成报工和审核都会再次检查 | 新入口不重算工资、不绕过数量校验 |
| 一张受管工序任务单只审核了部分产量 | 任务单通常仍是草稿；数量完成或与确认损耗合计达到任务量才提交 | 对“100 件任务先审核 40 件”不能承诺后序已经可以做 40 件 |
| 后序放行 | 读取工单工序的已完成数量；普通受管路径在前序任务单提交时更新该数量 | 按现有状态显示，部分报工与可接续量分别表达 |
| 快捷完工入库 | 有工序的路径要求工序任务完成；制造库存单还受全局受管草稿任务保护 | 部分完工入库是独立改动，原生页面也不能视为绕过入口 |
| 直耗料工单 | 正式派工检查现场料及优先分配，并可能创建硬预留；不走普通 WIP 发料申请 | 预览与人员建议不能提前调用正式派工 |

因此，前述“部分生产需要新做”的表述过宽。准确缺口是：首次部分发料后的新派工入口尚未与已有部分报工能力贯通。另一个需要修正的例子是“前序审核 40 件后自动流到后序”：当前受管任务的提交机制不保证这一点，本方案不会借页面改版改变该规则。

现有测试有明确边界：`test_production_readiness.py` 的部分物料用例同时断言可申请部分发料和不可派工；`test_worker_reporting.py` 的部分覆盖用例验证已有派工的开工、报工上限，但该套件的 setup mock 了正式派工门槛，不能用它证明首次发料到新派工全链路已通。实施验证另外增加了不 mock 派工门槛的真实领料集成测试。

**首版操作体验。**

生产计划中心增加“按订单查看／按工序派工”两个视图，共用同一套业务事实。旧的单工单详情和操作入口保留。

主管选择“切割”等工序后，看到跨订单、跨计划的任务。每行仍是一张确定的 Job Card，显示产品规格、工作站、来源订单与工单、交期、任务量和单位、当前派工情况及阻塞原因。同名工序可以一起查看，不表示实物可以混做；不同产品与单位不累加成一个无含义的总数。

主管勾选符合条件的任务，一次选择人员，查看逐任务分配预览，确认后系统逐张执行原有派工。比如当前有 6 张符合条件的切割任务，可以一次选择张三并确认 6 行；后台仍生成各卡独立的派工记录。任务数、数量、单位与所选范围应在确认前清楚展示，分页首版不提供隐含的“全选全部结果”。

第一版仅批量处理“当前可正式派工、没有保留的派工、报工、原生时间或数量移动记录，完成量及损耗量为零”的普通工序任务。旧入口合法撤销并删除尚未开工的安排后，可重新安排；首版不新增永久历史标记。已派工、已开工、退料释放后补派、需要替换原安排等情形链接现有单卡入口。

人员固定时，可把“本轮选择的人员”带入选中的其他任务。仅有一人时填入每张任务的全量；多人时仍逐卡按原有数量分配方式校验，总和必须等于该卡任务量。多人姓名只作为候选，不自动均分，不把每人都设置为整卡产量。

后序在原规则满足后进入可派列表，主管集中确认下一批。工人继续使用现有任务、开工、暂停、报工界面，一人同一时间一个进行中的作业会话，审核和工资快照沿用现状。

这版减少找单、开弹窗和重复选人的动作，仍需要主管在各阶段集中确认。它不能承诺“所有工序一次排完后完全无人干预”。如果主要等待来自审核速度、整卡提交或齐套条件，这些等待不会因新视图自动消失。

默认人员若后续持久化，作用域至少是公司与工序，有需要再限定工作站。冲突或失效时留待人工处理，不随意取一个规则。配置变化只影响后续建议；已有正式派工、人工修改与报工事实不随配置重写。业务权限仍按当前能力与公司范围检查，不能把“可查看计划中心”扩大为“可派工”，也不能擅自缩成“主管只能看自己派的任务”。

**领料、库存与追溯保持的业务关系。**

主管按工单申请，库房核对后发料到对应在制品仓；主管交料给工人属于实物交接，派工本身不再扣一遍原料。换人时继续按现有派工变更规则处理，同仓、同工单内换人不需要人为退库再领。实际跨仓移动仍保留库存单。

首版工序池可以展示缺料、已发料及入库待处理状态，并跳到现有动作。申请仍按单工单执行；发料已有部分申请和优先级调整继续可用。普通工序交接继续按进度记录，需要独立存放、盘点、领用的半成品保持现有库存收发。报工审核不直接增加成品库存，库房继续确认实际入库数量和批次。

追溯链继续使用订单来源、工单、工序任务、个人派工与报工、实际库存单及批次。页面汇总不创建新的库存“池”，也不放开对其他工单已预留物料的占用。原有报工未直接绑定实物子批次的精度边界仍然存在；首版既不降低也不声称增强到“每箱实物对应具体工人”。

未来批量申请库存动作时，应按用户明确确认的顺序逐工单生成原单，保留原料批次、数量和来源，不把多个工单改成一个无法分辨来源的总数。这一步需要独立验证共享物料优先级、硬预留和网络重试，不能作为无风险的界面按钮附带上线。

**最小实现边界。**

新增聚合读入口，尽量复用现有 `get_work_order_assignment_context` 的领域判断。它检查的不只是物料，还包括前序、工价、已有历史和特殊任务限制。分页加载并按工单去重查询，避免展开全部计划形成大量重复查询。展示建议、切换筛选和刷新均不得创建派工、预留、通知或修改业务时间戳。

写入需有一个很薄的“仅首次派工”服务包装。沿用现有权限及锁顺序，在锁内重查工序任务身份、数量、公司范围和“没有任何派工记录”等条件，再调用现有 `assign_workers`，不自行插入派工或修改库存。

这个包装是必要保护：原接口支持替换尚未开工的已有方案；如果新批量入口只看旧页面上的 `can_assign` 就调用它，可能覆盖另一名主管刚刚做出的安排。新入口不能拥有这种隐式替换能力。原单卡接口的现有行为保持。

批量在界面上是一组操作，后台逐卡顺序请求，每卡一个原有事务，并限制单次选中规模。一卡失败只回滚该卡，已成功行保留；结果显示成功、业务失败、已被他人处理、尚未处理、结果待核实。用户停止时只停止尚未提交的请求，不自动删除已成功派工。

网络超时先重读服务器事实，不能立即判定失败或盲目重放可覆盖方案的旧接口。服务端“仅首次”检查确保并发或重试不会生成第二份初次方案；已有方案若并非能确认来自本次请求，应显示已存在并要求核对，不能冒称本次成功。相同计划返回现有记录属于现有状态去重，不等于已经有完整的批量请求级幂等日志。

首版可沿用已有逐卡派工人、派工时间和变更审计。跨刷新恢复整个批量操作、完整批量请求审计不作为首版承诺，若需要则独立增加操作日志，不能复用库存 Batch 表充当操作批号。

**风险评估。**

等级为对当前改造的工程判断，不是故障概率测算；“影响小”不等于零风险。

| 风险 | 不设边界时的影响 | 首版措施 | 剩余风险判断 |
| --- | --- | --- | --- |
| 批量误选、混淆产品或单位 | 一次派错多张任务 | 每行展示来源、规格、单位和数量；确认选中范围；不合并不兼容总量 | 中，需要真实岗位验收 |
| 覆盖其他主管刚派出的方案 | 人员变更、通知和责任归属出错 | 锁内首次派工检查；有任何历史转原入口 | 中，必须并发验证 |
| 只凭材料状态推断可开工 | 越过前序、工价或任务支持范围 | 完整复用现有领域判断，提交时重查 | 低至中 |
| 批量请求超时或部分失败 | 重复执行、误认为全部完成 | 每卡事务；清楚列出结果；超时先核实；不回删成功记录 | 中 |
| 新读接口越权或数据混公司 | 泄漏其他公司的订单、员工或工资信息 | 复用能力和公司范围，服务器过滤，前端隐藏不作为权限保护 | 中 |
| 预派提前锁料 | 改变其他订单的可用库存 | 首版人员选择仅表单建议，未确认不调正式派工 | 首版不引入该新行为 |
| 统一报工、班组重复记产量 | 重复工资、成本和完成数量 | 首版保留个人逐卡报工及现有计时规则 | 首版不引入该新行为 |
| 拆改库存或批次归属 | 用料与产出追溯失真 | 库存写入路径不改、工单和批次明细保留 | 首版不引入该新行为 |
| 列表太大拖慢生产页面 | 影响日常操作 | 分页、按工单去重加载、限制查询范围，观察大数据量耗时 | 中，需性能验证 |
| 关闭新入口后任务无法继续 | 回退困难 | 新入口只生成原类型派工；旧入口继续可用 | 低，需关闭入口验收 |

全自动派工的后续风险至少为中等。即便继续遵守原有就绪条件，也要处理员工停用、审核人失权、工价变化、工单暂停、手动抢先安排、模板变更、重复事件和失败重试。它应在来源业务提交成功后独立执行，不能因自动派工故障使原报工审核或库存提交失败。自动派工也不自动开工计时。

**验收与上线顺序。**

先在隔离环境把同一组输入分别走旧单卡流程和新批量流程，比较业务结果；忽略单号和时间等预期差异，核对来源、人员、数量、权限、预留及工资规则一致。

| 验收场景 | 必须满足 |
| --- | --- |
| 多订单同工序、同一人员批量首次派工 | 分别生成原类型派工，来源和数量与旧入口一致 |
| 多人分量、整数单位、小数单位、重复员工或错误总量 | 沿用现有校验；失败的单卡不残留部分派工 |
| 两个主管同时派同一卡，或列表加载后被他人先处理 | 最多一个有效初次方案；新入口不覆盖先完成的安排 |
| 一卡失败、网络超时、重复点击、关闭页面后重进 | 每卡结果可核实；成功项不重复创建、锁料或通知 |
| 待料、部分发料、待前序、前序待审核、失效工价、暂停或终止工单 | 展示和写入均遵守旧入口条件 |
| 已有派工后退料、报废、隔离与补料 | 新视图不破坏既有个人额度及物料覆盖；变更走原入口 |
| 前序只部分报工审核、部分完工申请入库 | 不因新视图误放行；原有受管任务保护继续有效 |
| 直耗料、多工单竞争共享原料、批次物料 | 与逐卡旧入口相同的预留和批次结果；仅看页面不产生写入 |
| 已派工、已报工、已释放待补派及特殊 Job Card | 不被新批量首次派工修改；原详情和专用路径可达 |
| 生产主管、老板、库房、工人、无公司授权账户 | 读写权限和公司范围与现有能力一致，不暴露不必要工资数据 |
| 工人得到多个任务后开工、暂停、部分报工、审核及工资汇总 | 仍符合原有会话、数量和工资快照规则 |
| 在制工单、历史记录及关闭新入口 | 原入口能继续完成派工、报工、审核、领退料和入库 |
| 手机与多工单数据量 | 选中范围、结果可读；无明显加载退化，性能阈值以旧页面基线确定 |

上线采用三步：先开放只读工序视图并对照现有单卡结果；再对少量普通新任务启用批量首次派工；通过验收后扩大范围。历史派工不迁移、不自动套用人员建议。新增功能采用临时发布开关，旧入口保留。关闭新入口停止新批量操作，已生成记录继续按原流程使用；不自动删除派工，不回滚真实库存或报工事实。正在提交的一卡需完成或核实结果后再继续。

观察指标是找到并完成一批派工所需时间、重复选人次数、派错和人工修正次数、批量失败及待核实项、页面耗时。先记录旧流程基线，再对同类任务比较，不预先承诺具体效率提升百分比。

后续是否自动化取决于实测：如果主要时间确实消耗在每轮确认派工，可试点固定单人、普通工单、满足全部旧条件后的自动首次派工；如果主要耗时在找单与选人，首版可能已经足够。首次部分发料开工、部分工序流转和部分入库分别立项验证，不与自动化同时放开。
