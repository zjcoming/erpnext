# 恒算 ERP 原生批次兼容方案

日期：2026-09-14。代码基线：`6b482fcf57`；本机原生 ERPNext 源码版本：`16.33.0`。

状态：**本机实现及列明验证已完成，正式站尚未部署。** 本文件保留基线方案；实际改动、测试结果和交付边界见[实施与验证记录](batch_compatibility_validation_20260914.md)，工厂操作见[批次管理操作卡](batch_quick_start.md)。用户已确认保持现有生产计划及共享库存逻辑，不增加“生产计划专用库存”规则。

## 先读这一页

**推荐方案：沿用 ERPNext 的设置和单据，恒算负责把快捷流程接通。默认普通物料照常使用；需要批次的企业按物料开启，仓库使用原生页面确认实际批次。**

五个确定的设计决定：

1. **沿用一个设置体系。** 使用原生库存设置和物料“有批次”，不再增加恒算总开关。安装、升级均保留用户原有配置。
2. **销售和工人保持简单。** 快速开单仍填客户、产品、数量、单价、交期；工人仍按现有方式报工。
3. **仓库负责实际批次。** 收货、发料、完工入库、发货继续打开原生单据，使用原生批次选择器、自动编号及库存校验。
4. **区分数量预留和指定批次。** 普通销售预留遵循原生自动选批设置；普通工单可以先锁数量。已明确来源的完工回补、半成品和补产回补，必须保留来源批次。
5. **补齐恒算的外围功能。** 可用库存、岗位权限、待办提示、打印、查询和取消回退一起兼容，才算能够正常使用。

| 用户 | 不使用批次时 | 使用批次时增加的操作 |
|---|---|---|
| 管理员 | 使用现有库存设置 | 在原生设置启用功能，对指定物料开启批次；按需配置手动/自动编号及有效期 |
| 销售/老板 | 快速开单、看订单进度 | 开单方式不变；可看到产品按批次管理及可用数量 |
| 生产主管 | 排产、申请发料、申请入库 | 申请仍按数量；有明确来源的回补显示来源批次摘要 |
| 工人 | 开工、报工、异常申请 | 普通报工不增加批次必填项 |
| 库房 | 核对原生出入库单并提交 | 核对或选择实际批次；一行可以按原生方式分配多个批次 |
| 库存管理人员 | 查看库存和业务单据 | 使用获授权的原生批次库存、追溯报表 |

## 一、启用规则

### 默认行为与用户选择

- 新站点保持原生“未启用”的默认值；新建普通物料不自动勾选批次。
- 现有站点已开启的功能、物料标志、编号规则、自动选批方式均保留；升级脚本不得重置为 0。
- 是否按批次处理一条业务，**以该物料的 `has_batch_no` 为准**。全局激活开关主要控制原生物料设置入口，不能用它绕过既有批次物料的库存要求。
- 同一站点、同一订单和同一库存单允许普通物料与批次物料混用。仅原料开启、仅成品开启、原料和成品都开启，均属于本方案范围。
- 原生“自动创建批次”是可选方式；手动建立和选择批次同样可用。有效期也不强制启用。
- 保留原生自动选批开/关以及 `use_serial_batch_fields` 两种既有模式，不要求客户为了恒算切换整个站点的单据模式。
- 原生对已有相关已提交业务的物料属性变更、已有批次业务后的关闭限制照常生效。旧库存启用批次须另做库存切换方案；系统不能自动还原历史批次。

管理员入口提供“批次管理（可选）”说明及原生库存设置、物料配置链接。非批次业务不增加检查门槛或空白批次列；已有批次记录的查询入口不因开关状态被隐藏。

### 配置检查的表达

检查结果区分“可手动处理”“可自动处理”“本次单据缺少必要信息”。例如未设置自动编号，应提示可以手动建批次；只有本次入库既没有可用批次、也无法按原生规则创建时，才要求补齐。不能把某种自动化设置缺失变成整个批次功能不可用。

## 三、实现方式：集中补少量适配代码

### 1. 统一读取批次库存事实

建议增加一个小型 `batch_compat.py` 模块，供快捷开单、工作台、排产、缺料和定向回补共享。只组织原生查询及单据数据，不新增批次账表、持久化库存总数或独立选批算法。

它集中处理三件事：读取原生批次数量、提取来源单据批次分配、生成只读批次摘要。非批次物料直接使用现有路径；查询按请求缓存并批量读取物料标志，避免每行反复查库。

现有 `page_refresh.py` 的变更主题需要补充 Batch。批次禁用、有效期变更后通知相关页面重新读取；跨日、页面重新激活及执行动作时也要按当前日期重读，避免只有库存单提交才刷新。继续使用现有刷新机制和请求级缓存。

库存接口必须明确以下口径：

- **账面在库**：库存账及 Bin 的物理总量，允许与当前可执行量不同。
- **当前有效批次库存**：按原生单据用途、过账时间、仓库及批次规则可用的库存。有效期检查不使用会包含过期批次的 `for_stock_levels=True`。
- **已绑定批次的硬预留**：只计算尚未执行的余额，按原生批次规则处理。
- **尚未绑定批次的硬预留**：包括 Qty SRE、WO 空批次明细，以及明细尚未覆盖的剩余占用。
- **软承诺**：销售、工单、生产计划等已有计划需求，由现有分配算法继续去重处理。

不能把上述数字混成一个“库存”。原生批次数量查询通常已扣按批次预留和相关 POS 占用，却不会替恒算扣掉全部数量预留。执行池应在原生有效批次余量上**再扣一次未绑定批次的硬预留余额**，并遵守聚合库存上限；已扣的批次预留不能重复扣。

例：账面 100，有效批次 60，其中已绑定批次预留 20，另有数量预留 20，则可自由承诺量为 **20**。仅取“聚合可预留量与有效批次余量的较小值”会误得 40，不可采用。

计算“未绑定余额”时，应扣除所有真实绑定批次的未使用明细，包括已经失效的批次。已绑定但过期的10件是“绑定失效”，不能改算成10件自由数量预留后再占用健康批次。头部与子行的已执行量沿用当前原生/恒算重算语义，不在子行上重复扣除头部转移、耗用量。

生产齐套继续按原有优先级分配软承诺。给本工单加回自己的预留时，只能加回仍有效、可兑现的份额；已过期或不可用批次的预留不能重新变成“齐套”。页面清楚区分“已预留数量”和“当前可执行数量”。销售交期不被自动当作未来库存保证，实际单据提交时按原生日期规则重新校验。

实施时以混合 Qty/批次预留、WO 空明细、软承诺、自有预留及 POS 占用的对账案例锁定适配器契约，避免重新实现原生库存账。

### 2. 普通预留与来源回补分开处理

**普通销售预留：** `_new_sre` 不再仅因物料有批次就强制 Serial and Batch。让原生自动选批设置决定是否提前绑定，保持用户关闭自动选批时也能正常作业。

**普通工单预留：** 保留原生允许的数量占用方式。`reservation_based_on` 的文字值不能单独证明批次已锁定，应检查实际明细；库存适配器把没有批次明细的余额按数量占用处理。

**来源已经确定的回补：** 销售完工回补、半成品与补产回补共用来源分配辅助函数：

1. 验证来源为当前允许使用的已提交 Stock Entry 行，并匹配产品、目标仓库及业务归属。
2. 优先读取 `serial_and_batch_bundle`；兼容原生旧字段记录形式。
3. 按来源剩余可认领量、该批当前可用量及订单/工单剩余需求，计算本次分配。
4. 只把本次实际分配数量写入目标 SRE 的原生批次子表；不要整包复制，不把一个源 Bundle ID 直接复用为另一张业务单据的 Bundle。
5. 同来源重复回补、同一批次多次入库、部分释放、取消、退回均重算余额。来源批次 A 已转走时，不得用同仓 B 冒充该次完工回补。

沿用现有 Bin/SRE 事务锁、幂等和回滚机制；取得锁后重新读取批次余量。来源行和相关预留也要在同一事务内重验，不能按预览结果直接提交。批次内同一身份多次入库仍按原生批次粒度管理，不承诺单件唯一来源。

### 3. 原生单据承接实际操作

采购收货、生产发料、制造入库、销售发货继续使用已经存在的原生草稿入口。物料和数量变更后，由原生重新校验/选择批次；恒算不维护第二套弹窗或强行修改用户自动选批设置。

发货尤其检查原生映射出的多 SRE、多仓、多批次行：缩小发货数量时不能只修改 `qty` 而保留原批次整包数量。需要调整时在原生表单完成，由原生验证最后提交。

异常处理已有“核对实物并过账”的实时批次预览与确认，可继续保留。批次未确定、来源不明或用户需要改动时，明确引导打开原单核对；后台仍实时验证。

新增的来源回补校验只作用于恒算拥有的相应动作，保留全局 Stock Entry 钩子的现有用途/来源门控。普通无工单调拨、Repack、批次拆分不能被强制要求关联生产申请；Stock Reconciliation 和采购/销售发票更新库存继续使用原生权限及过账流程。普通库房不因此自动取得发票或盘点权限。

## 四、权限、查询与打印

### 岗位权限

在现有 `management_access.py` 岗位模型中补 Batch 和 Serial and Batch Bundle 必要权限，不把全部库房人员升级成 Stock Manager/System Manager。

- 库房默认取得正常收货、选批次所需的 Batch 选择/新建权限，以及 Bundle 读取/选择/新建/修改/提交权限。原生库存过账会提交 Bundle，真实岗位测试确认需要此权限。Batch 主档含全局数量，受限库房通过授权仓库的原生选择器操作；完整主档交给另外获授权的管理人员。预先存在的客户额外权限保留。
- 批次禁用、有效期修改等主数据管理由已有授权管理员负责；选择批次不应顺带获得任意批次维护权。
- 销售仅快速开单不需要新增批次主数据管理权限；确实承担原生批次预留的岗位再按工作职责授权。
- 保持公司、仓库和来源单据的现有访问范围。权限修订纳入已有安装/迁移机制，并保留客户自定义角色、权限和配置。

### 原生查询入口及真实边界

复用 `Available Batch Report`、`Batch-Wise Balance History`、`Serial No and Batch Traceability`。菜单按实际权限和批次业务显示，并检查直接 URL/API 访问。

**推荐最小交付策略：完整原生追溯报表先向具备全量库存查看权限的管理人员开放；受限库房通过其有权访问的业务单据核对批次。** 当前原生追溯查询没有公司/仓库筛选和完整权限过滤，不能简单给受限岗位加一个 Report 角色就声称保留了隔离。其他原生批次报表也需逐个验证范围。

若业务要求受限库房独立查完整追溯，则增加薄的权限包装，服务端过滤批次候选、每级原始单据及整个关联链；这应成为该角色开放报表的前置交付项。包装只限制可读结果，不另建追溯账或计算引擎；不能用前端筛选代替服务端权限。

**原生追溯粒度：** 本机源码以制造单投入/产出记录关联，部分材料数量按比例展示，正向查询存在只取一条成品/Bundle 子行的路径。因此可以承诺原生批次记账和可追溯单据；不能承诺同一制造单多投入、多产出批次都在该报表完整展开，或还原每件产品实际用料。

需要清楚区分每次成品批次来源的工厂，应按实际生产批次拆分制造入库单，分别记录实际耗用；多产出批次的原生报表表现列入验收并写入手册。如果发现原生版本问题影响承诺场景，单独提出可复现问题与扩展修复范围，不暗中修改原生核心。

### 打印和扫码

收货、库存、发货三个默认打印模板共用一个条件显示宏：在物料下显示“批次、该批数量、库存单位”。优先读单据实际 Bundle，兼容旧 `batch_no`；收货接收和拒收批次分别展示。普通物料打印保持现状，客户自定义模板遵守已有保护机制。

现有单据二维码继续“扫单据→打开原单→核对批次”。批次标签、按批次码扫码拣货是独立扩展，不作为基础批次管理的启用条件。

## 五、必须通过的验收

验收使用隔离测试站和真实岗位权限；不能只用 Administrator，也不能用现有退料单元测试替代整条流程验收。

| 编号 | 场景 | 必须得到的结果 |
|---|---|---|
| B01 | 全局默认未启用，全部普通物料 | 开单、排产、收发、报工、打印与现有行为一致 |
| B02 | 升级前已启用批次，另有历史批次记录 | 设置、物料属性和历史查询保持；不被迁移重置 |
| B03 | 仅原料、仅成品、二者都启用；同单混合物料 | 各组合均走通，普通行不增加批次要求 |

## 六、实施顺序与工作量

1. **先验证原生路径和角色。** 用新建测试批次物料，跑手动/自动选批、Qty与指定批次预留、普通WO发料、取消、纯库房权限，确认原生API契约及本版本边界。
2. **接通库存与来源。** 完成快速开单兼容、批次库存事实适配、销售和生产定向回补；统一页面显示与动作校验，保留现有事务保障。
3. **补现场使用。** 岗位权限、原生入口、待办摘要、三个打印模板、手册中的可选启用操作卡。
4. **跑完整验收再交付。** 覆盖上述场景、非批次回归、真实岗位浏览器操作，并记录原生报表边界。

按本方案最小交付路径，初步估算 **6–10人日**，包含开发、回归和岗位验收准备；这是源码审查后的估算，首轮原生契约验证后调整。此前3–6人日主要针对销售批次链路，本次增加了原料齐套、半成品回补、岗位和打印范围。受限角色完整追溯包装如被业务要求，另计其实施和权限验收工作量。

历史库存切换、旧单据批次补录、新批次标签、原生多产出追溯报表修复和生产部署验收应分别评估；它们不应被隐含计入“勾选后自动完成”。

交付标准：未使用批次的企业不用调整原操作；选择批次的企业可在授权岗位下走完收货、生产、销售和退回，并以原生库存记录核对。达到标准后再标记该兼容能力已交付。
